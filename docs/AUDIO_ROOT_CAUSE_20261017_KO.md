# C01 오디오 누수 원인 분리·수정 후보·독립 검증

2026-10-17 / Asia/Seoul. **최종 상태: BLOCKED. `AUDIO_LEAK_RESOLVED`를 선언하지 않습니다.**
설치된 Godot 4.7.1에서 원래 WASAPI 즉시 종료 조건이 여전히 실패합니다.
최소 재현 프로젝트와 엔진 종료 정리 패치를 준비했으나, 패치는 빌드·실행 검증되지 않았습니다.
PC 자동 종료는 수행하지 않았습니다.

## 1. 실제 확인한 원인

오디오를 로드하지 않거나 WAV를 로드만 하면 두 드라이버에서 모두 통과했습니다.
게임 코드 없이 WAV 하나를 재생하고 바로 종료하면 WASAPI·Dummy에서 각각 5/5 실패했습니다.
따라서 C01의 UI, 저장, 퍼즐 코드가 없어도 발생하는 엔진 종료 수명 문제입니다.

플레이어를 stop하고 stream=null 및 free까지 완료해 트리에 root 하나만 남긴 뒤에도
playback WeakRef와 WAV WeakRef가 살아 있었습니다. 이후 믹서와 메인 루프가 진행되면
두 참조가 모두 소멸했습니다. 예를 들어 최소 프로젝트의 한 WASAPI 실행에서는
노드 해제 직후 playback WeakRef 300개·stream WeakRef 3개가 남았다가 약 14.7ms 뒤 0이 됐습니다.
WeakRef 개수는 참조 항목 수이며, 같은 객체를 여러 번 기록한 경우의 고유 객체 수로 해석하지 않습니다.
실제 누수 객체 수는 별도로 Godot의 `Leaked instance` 진단에서 셌습니다.

실행 바이너리가 보고한 커밋 접두사 `a13da4feb`와 공식 `4.7.1-stable`의 해당 소스가
바이트 단위로 일치함도 확인했습니다. 해당 버전의 수명 경로는 다음과 같습니다.

```text
AudioStreamPlayer.stop()/노드 해제
  → 서버 playback을 FADE_OUT_TO_DELETION으로 표시
  → 이후 오디오 mix 단계가 목록에서 제거 예약
  → 메인 스레드 cleanup이 실제 playback 참조를 해제
```

문제는 `AudioServer::finish()`가 드라이버를 정지하면서도 아직 살아 있는 playback 목록을
명시적으로 비우지 않는다는 점입니다. 이후 mix가 없으면 해당 항목이 삭제 대기 목록으로
넘어가지 않습니다. `SafeList::maybe_cleanup()`은 이미 삭제 예약된 항목만 회수합니다.
플레이어의 참조를 비우거나 믹서 lock/unlock을 하는 것만으로 이 서버 참조가 사라지지 않습니다.
이는 최소 재현의 관찰과 해당 버전 소스를 결합한 결론이며, 엔진에 네이티브 디버거를 붙여
각 C++ 참조의 호출 스택까지 기록한 것은 아닙니다.

근거: [AudioServer 4.7.1 소스](https://github.com/godotengine/godot/blob/4.7.1-stable/servers/audio/audio_server.cpp),
[SafeList 소스](https://github.com/godotengine/godot/blob/4.7.1-stable/core/templates/safe_list.h),
[플레이어 내부 수명 코드](https://github.com/godotengine/godot/blob/4.7.1-stable/scene/audio/audio_stream_player_internal.cpp).
[공식 이슈 #76745](https://github.com/godotengine/godot/issues/76745)의 비동기 참조 분석과
현재 열린 [수정 PR #122742](https://github.com/godotengine/godot/pull/122742)도 같은 경로를 설명합니다.
[이슈 #95484](https://github.com/godotengine/godot/issues/95484)는 유사 증상의 참고 자료로만 사용했습니다.

## 2. 게임 코드·테스트·엔진의 구분

- 게임: 반복 play는 이전 voice를 서버의 비동기 회수 경로에 남겨 증상을 증폭할 수 있습니다.
  그러나 정상 API 사용만으로도 최소 프로젝트에서 재현되므로, 게임 참조 정리 누락만의 문제는 아닙니다.
  기존 `_exit_tree()`의 stop/null 처리도 서버 목록의 즉시 회수를 보장하지 않습니다.
- 테스트: 프레임 없이 재생을 반복하고 같은 프레임에 종료하는 검사는 실제 조작보다 극단적입니다.
  하지만 이번 필수 수용 조건이며 삭제하거나 약화하지 않았습니다. WeakRef를 사용한 실험과
  WeakRef도 없는 원래 스크립트 모두 재현됩니다. 테스트가 playback을 강하게 보관해서 생긴
  가짜 누수만으로 설명할 수 없습니다.
- 엔진: 믹서의 삭제 처리와 종료 순서가 경합합니다. 한 프레임 기다리는 검사나 5회 전부 통과한
  소그룹도 문제 해결의 증거가 아닙니다. 계측과 실행 속도에 따라 재현 빈도가 달라집니다.
- 드라이버: `--headless`의 기본은 Dummy입니다. 이번 실제 오디오 검사에서는 그 뒤에
  `--audio-driver WASAPI`를 명시하고, AudioServer의 드라이버 이름 또는 WASAPI 장치 활성화 로그를 확인했습니다.

## 4. 구현한 수정 후보와 적용 범위

1. `.autodev/audio_lab/`에 재현 프로젝트 생성기, 원래 즉시 종료 스크립트의 보존 복사본,
   프로세스별 격리 환경, 유일한 로그와 상태 기록을 구현했습니다.
2. 임의 고정 대기 대신 실제 WeakRef 소멸을 종료 조건으로 삼는 E_drain/H_drain 실험을 구현했습니다.
   2초는 실패 상한이며 성공을 위한 고정 대기가 아닙니다. WASAPI에서 관찰한 참조 회수 지연은
   최소 프로젝트 중앙값 16.86ms/최대 21.88ms, 원본 게임 중앙값 6.11ms/최대 22.37ms였습니다.
   이 완화 경로의 통과는 같은 프레임의 원래 즉시 종료 조건을 해결했다는 뜻이 아닙니다.
   게임 원본에 적용하거나 안정 기능으로 통합하지 않았습니다.
3. [검토용 엔진 패치](../.autodev/audio_lab/engine_patch/godot-4.7.1-drain-at-finish.patch)를 준비했습니다.
   `AudioServer::finish()`에서 모든 드라이버 정지 후 잔여 playback을 기존 삭제 함수로 제거하고,
   버스 삭제 전에 회수하도록 한 함수만 변경합니다. 정확한 공식 소스 복사본에 `git apply --check`가 통과했습니다.
4. 현재 PATH에서 Windows C++/SCons와 WSL C++/SCons 도구를 찾지 못했습니다.
   새 의존성을 설치하지 않았고 패치를 컴파일·링크·실행하지 못했습니다.
   기존 Godot와 export template도 교체하지 않았습니다. 따라서 패치 적용 후의 실제 결과는 **미검증**입니다.

공식 `4.7-stable`, `4.7.1-stable`, 바이너리 커밋 접두사의 AudioServer 소스는 일치했습니다.
조회한 master에도 finish의 명시적 playback drain은 없었습니다. 다른 버전의 바이너리를
실행 비교한 것은 아니며, 고쳐진 공식 릴리스가 있다고 단정하지 않습니다.
참조 원문·SHA·검토용 변경 소스는 로컬 `references/`에 보존했습니다.

생성 EXE의 시작·종료 검사는 오디오 스트레스 전체를 대신하지 않습니다.

로그 판정기 검사 10건은 모두 통과했습니다. 기존 하네스 111건은 Windows에서 100 통과·
11 Linux 전용 skip이었습니다. 새 진단기를 포함한 오케스트레이터 검사 34건은 33 통과·
1 symlink 권한 skip, 트랜잭션 검사 6건은 모두 통과했습니다. 건너뛴 검사를 통과로 계산하지 않습니다.
Python 구문 검사와 `git diff --check`도 수행했습니다.

별도 Windows Python 프로세스의 감사기는 runner의 판정 함수를 사용하지 않고 원본 로그
해시·드라이버·완료 표시·오류·누수 진단을 다시 검사했습니다. 320개 로그 모두 일치했고
독립 판정도 243 통과·77 실패입니다. 감사 자료가 일관된다는 뜻이며 오디오 해결 판정은 아닙니다.
감사 결과는 `AUDIO_LEAK_RESOLVED=false`, `BLOCKED`입니다.

## 6. 보존·E2E·남은 위험

시작 HEAD는 `30f37f5`이며 개발 브랜치는 `codex/autonomous-harness-20261017`입니다.
안정 브랜치 `c01-stable-slice-20261013`는 `83294f2`로 유지했습니다.
게임 원본 파일, 이전 실패 run과 `ui_hierarchy_01` 검토 결과는 변경하지 않았습니다.
기존 `.autodev/state`의 task_1=BLOCKED, task_2=PENDING도 그대로 보존했습니다.

오디오 해결 조건을 만족하지 못했으므로 **task_1 → task_2 실제 연속 E2E는 재개하지 않았습니다**.
과거 source_commit 검사를 우회하거나 실패한 후보를 통합하지 않았습니다.
이후 별도 엔진 빌드가 가능해지면 안정 엔진을 보존한 채 동일 원본 스크립트의 WASAPI 30회,
전체 회귀 검사와 export template까지 다시 검증해야 합니다. 그때 현재 HEAD에서 새 작업을
생성해야 하며 과거 run을 강제로 받아들이면 안 됩니다.

엔진 패치는 전체 오디오 서버 종료 순서를 건드리므로 콜백·확장 기능·오디오 장치 실패 경로의
회귀 위험이 있습니다. 소스 패치의 기계적 적용 검사는 런타임 안전 증명이 아닙니다.
참조 소멸 기반 종료 절차는 가능한 완화책이지만 외부의 즉시 quit/free까지 보장하지 못합니다.
실제 청취·믹싱 클리핑과 모든 환경의 안전성은 검증 완료가 아닙니다.
